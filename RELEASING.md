# Releasing Capsula

This document describes how to cut a Capsula release and how the release automation works.

A release publishes:

- the workspace crates to [crates.io](https://crates.io/crates/capsula),
- the `capsula-server` Docker image to [GHCR](https://github.com/ut-issl/capsula/pkgs/container/capsula-server), and
- a [GitHub Release](https://github.com/ut-issl/capsula/releases) with prebuilt `capsula` binaries, shell and PowerShell installers, checksums, and build attestations.

All of them are produced by a single run of the `Release` workflow (`.github/workflows/release.yaml`).

## Release procedure

### 1. Prepare the release pull request

On a new branch from `main`:

1. Bump the version.
   Update `version` in `[workspace.package]` of `Cargo.toml` and the `version` of every `capsula-*` entry in `[workspace.dependencies]` to the new version, for example `0.16.0`.
   Then refresh the lockfile with `cargo update --workspace`.
2. Write the release notes in `CHANGELOG.md`.
   Add a section whose heading is exactly `## v<version>` (for example `## v0.16.0`) above the previous release.
   Use `###` for subsections such as `### Breaking Changes`.
   This section becomes the body of the GitHub Release verbatim, and its heading text becomes the release title.
3. Open the pull request and merge it into `main` after CI passes.

The `Release` workflow also runs `dist plan` on every pull request, so a broken dist configuration is caught before merging.

### 2. Optional: dry run

In the GitHub Actions tab, run the `Release` workflow with the `mode` input left at its default `dry-run`.
A dry run can be started from any branch.

A dry run checks the crates.io preconditions and builds every binary archive, but it skips the CHANGELOG check, does not build the Docker image, and publishes nothing.
The built archives can be downloaded from the run's artifacts to try them locally.

### 3. Run the release

Run the `Release` workflow on `main` with `mode` set to `release`.

The workflow releases the version in `Cargo.toml` as the tag `v<version>`, for example `v0.16.0`.
Do not push the tag yourself.
The workflow creates the tag on the dispatched commit when it creates the GitHub Release.

### 4. Verify the release

After the run succeeds, check that:

- the GitHub Release has the expected title, body, and assets (five archives, `capsula-installer.sh`, `capsula-installer.ps1`, `sha256.sum`, `source.tar.gz`, and `dist-manifest.json`), and is marked as the latest release;
- the new version is listed on crates.io for every published crate;
- the `capsula-server` image is tagged with the new version on GHCR;
- an installer works, for example:

  ```sh
  curl --proto '=https' --tlsv1.2 -LsSf https://github.com/ut-issl/capsula/releases/latest/download/capsula-installer.sh | sh
  capsula --version
  ```

- the attestation of a downloaded archive verifies:

  ```sh
  gh attestation verify capsula-aarch64-apple-darwin.tar.gz --repo ut-issl/capsula
  ```

- `cargo binstall` downloads the new archive:

  ```sh
  cargo binstall capsula
  ```

## How the release automation works

### Overview

The binaries are built and released with [dist](https://axodotdev.github.io/cargo-dist/) (formerly cargo-dist), configured in `dist-workspace.toml`.
`.github/workflows/release.yaml` was generated by `dist generate` and is now maintained by hand: actions are pinned by commit, permissions are granted per job, and template expansions go through environment variables.
`allow-dirty = ["ci"]` in `dist-workspace.toml` tells dist not to regenerate or check the workflow.

The workflow runs these jobs in order:

```text
plan ─┬─> build-local-artifacts (5 runners) ─> build-global-artifacts ─> host ─┬─> publish-crates ─┬─> announce
precondition ─┘                                                                 └─> publish-docker ─┘
```

| Job | What it does | Runs on dry run |
| --- | --- | --- |
| `plan` | Runs `dist plan` to compute the build matrix. On a release, it also derives the tag from the version, checks that the run is on `main` and the tag does not exist yet, and runs `dist host --steps=create --tag=<tag>` to compute the release manifest. | Yes |
| `precondition` | Calls `release-precondition.yaml`: checks the CHANGELOG section (release only) and the crates.io Trusted Publishing settings. | Yes |
| `build-local-artifacts` | Builds the `capsula` binary and its archive on one native runner per target. | Yes |
| `build-global-artifacts` | Builds the installers, `sha256.sum`, and `source.tar.gz`. | Yes |
| `host` | Finalizes the dist manifest, including the release title and body. | No |
| `publish-crates` | Calls `publish-crates.yaml`: publishes the workspace crates to crates.io. | No |
| `publish-docker` | Calls `publish-docker.yaml`: builds and pushes the `capsula-server` image (amd64 and arm64) to GHCR. | No |
| `announce` | Attests the artifacts and creates the GitHub Release and its tag. | No |

Nothing is published before every build succeeds, and the GitHub Release is created only after both publish jobs succeed.

### Targets and runners

| Target | Runner | Archive |
| --- | --- | --- |
| `aarch64-apple-darwin` | `macos-latest` | `.tar.gz` |
| `x86_64-apple-darwin` | `macos-15-intel` | `.tar.gz` |
| `aarch64-unknown-linux-musl` | `ubuntu-24.04-arm` | `.tar.gz` |
| `x86_64-unknown-linux-musl` | `ubuntu-latest` | `.tar.gz` |
| `x86_64-pc-windows-msvc` | `windows-latest` | `.zip` |

Every target is built natively instead of cross-compiled.
The Linux binaries are statically linked against musl so that they run on any distribution.
Binaries are built with the `dist` Cargo profile, which is `release` with thin LTO.

Only the `capsula` package (the CLI) produces binaries.
`capsula-server` sets `dist = false` in `[package.metadata.dist]` because it is distributed as a Docker image.

### Release notes

dist reads the release notes from `CHANGELOG.md` (`create-release = true`, `github-release = "announce"`).
It takes the section whose heading matches the released version, uses the heading text as the release title, and appends install instructions and a download table to the body.

`scripts/check-changelog-release.nu` runs in the `precondition` job of a real release and fails the run before anything is built when the section for the version in `Cargo.toml` is missing.

### Version and tag

The workflow has no tag input.
The `plan` job reads the version of the `capsula` package from the `dist plan` manifest and releases it as the tag `v<version>`, so the tag always matches the workspace version in `Cargo.toml`.
A release fails early when that tag already exists, which means the version was not bumped.

### Docker image

`publish-docker.yaml` builds the image from the dispatched commit, because the release tag is created later by the `announce` job.
It tags the image with `<major>.<minor>.<patch>`, `<major>.<minor>`, `<major>`, and `latest`, using the tag from the dist manifest.
It does not use the GitHub Actions cache, so that a release build cannot read cache entries written by other workflows.

### `cargo binstall`

`[package.metadata.binstall]` in `crates/capsula-cli/Cargo.toml` points [cargo-binstall](https://github.com/cargo-bins/cargo-binstall) at the archives of the GitHub Release, so `cargo binstall` installs the same binaries as the installers.
It disables the `quick-install` strategy so that targets without an archive are built from source instead of falling back to third-party binaries.
cargo-binstall reads this metadata from the crates.io package, so a change takes effect from the next release.
When the archive names or layout change, update the metadata and test it before releasing:

```sh
cargo binstall --manifest-path crates/capsula-cli --targets <target> --install-path <scratch-dir> --no-track capsula
```

### crates.io Trusted Publishing

The crates are published without an API token through [Trusted Publishing](https://crates.io/docs/trusted-publishing).
`publish-crates.yaml` exchanges the workflow's OIDC token for a short-lived crates.io token with `rust-lang/crates-io-auth-action` and runs `cargo publish --workspace`.

crates.io matches the publisher by repository, the top-level workflow file, and the GitHub environment.
For this reason:

- the workflow file must stay named `release.yaml`, because a reusable workflow such as `publish-crates.yaml` is identified by its caller;
- the publish job must use the `release` environment.

`scripts/check-crates-io-release.nu` runs in the `precondition` job and checks that every crate to be published already exists on crates.io and has "Require Trusted Publishing" enabled.
A new crate must be published once by hand and configured for Trusted Publishing before it can be released by the workflow.

### Supply-chain safeguards

- Every action is pinned by commit SHA.
- dist itself is installed by `.github/actions/install-dist` from its GitHub release with a pinned SHA-256 checksum instead of `curl | sh`.
  Keep its version in sync with `cargo-dist-version` in `dist-workspace.toml`.
- Each job gets only the permissions it needs; only `announce` can write to the repository.
- The `announce` job creates [GitHub artifact attestations](https://docs.github.com/en/actions/security-for-github-actions/using-artifact-attestations) for the archives, installers, and manifest.

## Troubleshooting

- **`precondition` fails on the CHANGELOG check.**
  Add or fix the `## v<version>` section in `CHANGELOG.md` on `main`, then run the workflow again.
  Nothing has been published.
- **`plan` fails because the tag already exists.**
  The version in `Cargo.toml` was already released.
  Merge the version bump into `main` first.
- **`plan` fails because the run is not on `main`.**
  Start the release from `main`.
- **A build fails.**
  Nothing has been published.
  Fix the cause on `main` and run the workflow again.
- **`publish-crates` fails partway.**
  crates.io versions cannot be overwritten, so some crates may already be published.
  If no crate was uploaded yet (for example, the token exchange failed), fix the cause and re-run the failed jobs of the same run.
  Otherwise a re-run fails on the crates that are already published, because `cargo publish --workspace` has no option to skip them.
  In that case, bump to the next version and release that instead.
- **`publish-docker` fails.**
  Image tags can be pushed again, so re-run the failed jobs of the same run.
- **`announce` fails after the publish jobs succeed.**
  The crates and the image are published but no GitHub Release or tag exists yet.
  Re-run the failed jobs of the same run instead of starting a new run, which would try to publish the crates again.

## Updating dist

1. Update `cargo-dist-version` in `dist-workspace.toml`.
2. Update the version and the SHA-256 checksums of every platform archive in `.github/actions/install-dist/action.yaml`.
3. Compare the template of the new version with `release.yaml` by running `dist generate` in a scratch checkout, and port relevant changes by hand.
4. Run the `Release` workflow with `mode: dry-run` to check the builds.
