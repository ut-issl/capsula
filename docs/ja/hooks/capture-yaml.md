# capture-yaml { #capture-yaml }

1 つの YAML ファイルをパースし、その内容をラン出力の `content` フィールドに埋め込みます。

## ユースケース { #use-cases }

- 実験のハイパーパラメーターをラン間で検索できるようにする
- スクリプトが使った設定そのものを、構造化されたインデックス可能な形で記録する
- 複数の `capture-yaml` エントリーを組み合わせて、複数の設定ファイルを記録する

## 設定 { #configuration }

### 必須オプション { #required-options }

| オプション | 型 | 説明 |
| ------ | ------ | ----------------------------------------------------------------------------------------- |
| `path` | string | パースする YAML ファイルのパス。プロジェクトルートからの相対パスです。絶対パスも指定できます。 |

### 例 { #example }

```toml
[[pre-run.hooks]]
id = "capture-yaml"
path = "config/sat1/orbit.yaml"
```

## 出力例 { #output-example }

`content` フィールドには、パースされて JSON に変換された YAML が入ります。設定したパスは出力本体には重複して含まれません。オーケストレーターが付与する標準の `__meta.config.path` フィールドにすでに保存されているためです。

`config/sat1/orbit.yaml` が次の内容の場合:

```yaml
orbit:
  a: 1.42
  b: LEO
```

フックの出力は次のとおりです:

```json
{
  "__meta": {
    "id": "capture-yaml",
    "config": {
      "path": "config/sat1/orbit.yaml"
    },
    "success": true
  },
  "content": {
    "orbit": {
      "a": 1.42,
      "b": "LEO"
    }
  }
}
```

複数の `capture-yaml` の出力を区別するには、`__meta.config.path` で絞り込んでください。

## 複数ファイルの組み合わせ { #composing-multiple-files }

このフックは、1 つのインスタンスにつきちょうど 1 つのファイルを記録します。すべての設定ファイルを記録するには、設定ファイルごとにエントリーを 1 つずつ登録してください:

```toml
[[pre-run.hooks]]
id = "capture-yaml"
path = "config/sat1/orbit.yaml"

[[pre-run.hooks]]
id = "capture-yaml"
path = "config/sat2/orbit.yaml"
```

各エントリーは `pre-run.json` にそれぞれ独自の行を生成し、それぞれが独自の `content` フィールドを持ちます。設定したパスは `__meta.config.path` から参照できます。

## YAML から JSON への変換 { #yaml-json-conversion }

記録の仕様は意図的に最小限にしています。出力は [`yaml_serde`](https://crates.io/crates/yaml_serde) が型指定なしで JSON にデシリアライズした結果そのものであり、このフックは独自の検証を一切加えません。JSON で表現できる素直な YAML は、期待どおりに対応付けられます:

| YAML | JSON |
| ----------------------------- | ---------------------------------------------- |
| 文字列 / 整数 / 真偽値 | 対応する JSON の型 |
| 浮動小数点数 | JSON の数値 (`.nan` / `±.inf` は `null` になります) |
| null (`~`、`null`、空) | JSON の `null` |
| シーケンス (`- item`) | JSON の配列 |
| マッピング (`key: value`) | JSON のオブジェクト |

TOML と異なり、YAML には専用の日時型がありません。プレーンなスカラーとして書かれたタイムスタンプは文字列として記録されます。

### エッジケースの動作 { #edge-case-behaviour }

次の表は、`yaml_serde` クレートが提供するパーサーの注目すべき動作の一部を示したものです。すべてを網羅したものではなく、これらの動作は Capsula が保証するものではありません。

| YAML の入力 | 動作 |
| -------------------------------------- | ---------------------------------------------------- |
| 複数ドキュメントのストリーム (`---`) | パースエラー |
| アンカー / エイリアス (`&a` / `*a`) | 参照先の値に展開されます |
| マージキー (`<<: *a`) | **適用されません** — リテラルの `"<<"` キーとして記録されます |
| 文字列以外のスカラーキー (`1:`、`true:`) | 文字列化されます (`"1"`、`"true"`) |
| 文字列化した結果のキーの衝突 | **後に書いた方が優先されます** — もう一方の値は破棄されます |
| `!!binary` の値 | 生の base64 文字列として記録されます |
| カスタムタグ (`!Custom`) | パースエラー |
| スカラー以外のマッピングキー (`[1, 2]:`) | パースエラー |

YAML がマージキー、文字列以外のキー、タグに依存している場合、記録される JSON は YAML の実際の意味と一致しないことがあります。これらのエッジケースを避けるには、記録するファイルを JSON で表現できる素直な YAML に留めてください。

## エラー時の動作 { #error-behaviour }

次の場合、フックは失敗します (`__meta.success: false` として記録されます):

- ファイルが存在しない、または読み取れない (`Io` エラー)
- ファイルの内容が有効な YAML ではない、または上の表でパースエラーとした YAML の機能を使っている (`Yaml` エラー)

`capture-yaml` が失敗しても、他のフックの実行は止まりません。
